# BE-114 staging deployment, rotation, rollback, and smoke record

**Status: complete.** The staging environment was deployed on Railway, a secret rotation and a rollback were exercised, and on 2026-09-20 the full fictional journey ran on it: **24 of 24 steps passed**. The run reached the private API through a temporary public domain that was removed afterwards, not through a registered SSH key.

## Environment

- Railway project `shaidago-staging`, environment `staging` (a separate project from any production project; nothing shared).
- Services: `postgres` (`pgvector/pgvector:pg18` with a volume), `Redis` (managed), a private bucket, and `api`, `worker` and `migrate` built from `services/platform/Dockerfile`. None has a public domain in its normal state; there is no web service yet.
- Each service is limited to **1,024 MB** of memory and 2 vCPU on this plan.
- Providers: `PROVIDER_MODE=replay` (no live provider key), `SCANNER_MODE=not_deployed` (the hosted demo mode). All keys and role passwords were generated by `scripts/railway_staging_variables.py` and never printed or committed.
- Local embeddings: `EMBEDDING_BACKEND=fastembed` with the 129 MB `multilingual-e5-small` model baked into the image (ADR-0010).
- Deployed from commit `9fdbd7c` (`api`, `worker`, `migrate`).

## The smoke journey

Run once against the temporary domain, using the container's own internal credential and a staging reviewer, by `scripts/staging_smoke.py`. It prints one line per step and never a tracking code, credential, session token or report text.

```text
PASS readiness is ready
PASS public project read is cacheable and cited-only
PASS public list is paginated
PASS anonymous fictional report accepted and unpublished
PASS tracking shows a public-safe status and no report text
PASS an unknown code is one generic not-found
PASS reviewer signs in
PASS reviewer sees the report in the queue without its text
PASS reviewer detail decrypts the description
PASS reviewer transition applies and publishes nothing
PASS a stale decision is refused
PASS tracking reflects the decision
PASS reviewer verifies the report for a public update
PASS a separately authored update previews exactly and blocks nothing
PASS publication needs the previewed digest and shows the public update with its citation
PASS Q&A answers or falls back honestly (replay)
PASS public discovery run created or reused
PASS the worker completes the run from replay fixtures
PASS every result is labelled not yet reviewed
PASS reviewer approves an exact query and starts a report-scoped run
PASS the report-scoped run is invisible to the public
PASS reviewer signs out
PASS the revoked session no longer works
PASS the internal credential alone is not reviewer authority
24/24 steps passed
```

While the domain existed, an unauthenticated request to the API got the generic `401` problem response, so the internal-credential boundary held from the internet. The domain was then deleted (`railway domain delete`); the platform edge now answers `404` for it.

## What went wrong on the way, and what was changed

Recording these matters more than the pass.

1. **The seed could not run in a container.** It loads `scripts/validate_source_register.py` at run time, which the image never copied and `.dockerignore` excluded. Fixed in both places.
2. **Seeded facts were invisible.** The seed left every source version `pending` and every fact `draft`, and nothing in the product could approve a version, so public project pages showed no facts at all. The brief requires showing "awaiting verification" claims, but a database constraint forbade publishing one. Fixed by migrations 0025 and 0026 and by seeding approved versions whose passage hashes the register validator has re-checked. That approves the quoted text, not the claim.
3. **The first smoke run scored 21 of 24 for the wrong reasons.** It was run against real projects, but the replay fixtures are keyed to a fictional project and a test update must never land on a real project's page. Fixed by seeding the fictional fixture and letting the script discover the version to cite from the public page.
4. **The 2.2 GB embedding model was killed for memory.** It needs about 2.1 GB, and the service limit is 1 GB, so it restarted in a loop until the deployment failed. Measuring smaller siblings led to the 129 MB model (ADR-0010). During that attempt staging was briefly `unavailable`, because the database had already been migrated to a revision the running app did not know; readiness refused to report ready, which is the intended safeguard. Service was restored by redeploying without the model.
5. **`railway redeploy` did not apply a changed start command.** It re-runs the deployment's captured configuration. A fresh `railway up` was needed. Now in `docs/RUNBOOKS.md`.

## Limits

- Replay providers only; no live provider was involved in the smoke journey.
- The scanner is not deployed; files would be labelled `not_scanned_demo`.
- No CDN or web service sits in front of the API.
- The smoke reviewer's credentials are stored as staging variables on the `migrate` service (`STAGING_REVIEWER_IDENTIFIER`, `STAGING_REVIEWER_PASSWORD`). They open only fictional and seeded public data and should be rotated before any wider use.
- Memory headroom on the `api` service is 17% at peak. It fits, but it is not roomy, and a heavier model would not.
- `railway ssh`, which one runbook uses, was not exercised: no SSH key is registered on the account.
- No production project, backup or restore drill exists. Those remain production-gate items.
